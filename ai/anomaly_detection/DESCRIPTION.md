## 1. Project Overview & Objective

본 문서는 카메라 비전을 활용하여 단일 규격 우산의 파손(우산살 휘어짐, 원단 찢어짐, 장력 붕괴 등)을 감지하는 **이상 탐지**(Anomaly Detection) 시스템
정상 우산의 시각적 패턴(측면 사광 조명에 따른 장력 능선, 질감)만을 학습하여, 이로부터 벗어난 비정상 상태를 자동으로 판별하는 1-Class Classification 모델을 구현

---

## 2. Environment & Tech Stack

- **Language:** Python **3.10** (학습·추론 공통 — JetPack 6 기본값과 일치)
- **Core Library:** `anomalib` **2.5.1**(핀), `torch`, `torchvision`
- **Umbrella Detection:** `ultralytics` (YOLOv8n, COCO 사전학습 `umbrella` 클래스) — 파손 판정 전
  게이트. (venv에 이미 설치됨)
- **Image Processing:** `opencv-python`, `PIL`
  - ⚠️ `albumentations`는 쓰지 않는다. PatchCore에 증강을 넣으면 정상 분포가 인위적으로 넓어져
    파손 탐지력이 떨어진다(Step 1 참고). 전처리는 크롭·리사이즈·정규화 3단계로 제한한다.
  - ⚠️ `anomalib` 설치 시 `opencv-python-headless`가 딸려와 `cv2.imshow`를 죽인다.
    설치 후 `opencv-python`을 force-reinstall할 것 → `requirements.txt` 참고.
- **Model Architecture:** **PatchCore**(파손 판정, 이상 탐지) + **YOLOv8n**(우산 탐지 게이트)

### 실행 환경 분리 (학습 vs 추론)

| 구분 | 환경 | 목적 | 비고 |
| --- | --- | --- | --- |
| **학습(Training)** | GPU 서버 / 개발 PC (x86_64 + NVIDIA GPU, CUDA) | PatchCore 메모리뱅크 구축, 임계값 산출, **ONNX 내보내기** | `requirements.txt` (anomalib 2.5.1) |
| **추론(Inference)** | **Jetson Orin Nano** (**JetPack 6** / Ubuntu 22.04, Python 3.10, CUDA 12.x) | ONNX로 반납 우산 파손 판정 | **anomalib 불필요** — ONNX Runtime 또는 TensorRT |

#### 배포 형식: `.ckpt`가 아니라 **ONNX** (확정)

`train.py`는 `.ckpt`와 함께 **ONNX**를 내보낸다. Jetson에는 **ONNX + `metadata.json`만 올린다.**

- **이유**: `.ckpt`로 배포하면 Jetson에 `anomalib`·`lightning`·`timm`·`scikit-image`·`imagecodecs`
  등을 전부 설치해야 하고, **ARM64 휠이 없으면 소스 빌드**로 시간을 태운다. 또 학습·추론의
  anomalib/torch 버전을 계속 일치시켜야 하는 족쇄가 생긴다. ONNX는 이 의존성을 **통째로 제거**한다.
- 판정에 필요한 값(ROI·입력크기·정규화·`rawThreshold`·`scoreMin/Max`·밴드)은 전부
  **`metadata.json`에 명시**되므로, 추론 측은 anomalib 내부 구현을 몰라도 판정을 재현할 수 있다.
- ⚠️ **ONNX 수치 동등성 검증은 GATE-005 필수 항목**이다. PatchCore 내보내기 시 메모리뱅크 크기·
  이웃 수가 **상수로 고정(trace)** 되므로, 학습 측 torch 추론과 Jetson ONNX 추론의 anomaly score가
  일치하는지 동일 이미지로 대조한다. 불일치하면 임계값이 그대로 어긋난다.
- 입력은 **고정 크기(1×3×256×256)** 로 내보낸다. 동적 배치는 쓰지 않는다.

> **JetPack 6 torch 휠(참고)**: Jetson에서 torch가 필요한 경우(ONNX를 쓰지 않는 폴백 경로)는
> **NVIDIA Jetson 전용 휠**을 써야 한다. PyPI의 `pip install torch`는 x86용이라 CUDA가 붙지 않는다.
> 구체 버전은 **본인 JetPack 6.x 마이너 릴리스에 맞춰** NVIDIA 문서에서 확인해 확정한다
> (릴리스마다 CUDA·torch 버전이 다름). ONNX 경로를 쓰면 이 문제 자체가 발생하지 않는다.

#### JetPack 6 호환성 검증 결과 (2026-07-22, 개발 PC에서 실측)

**Jetson 실기 없이 x86에서 확인 가능한 항목을 모두 검증했다.** 통과 항목은 재검증 불필요,
미검증 항목은 GATE-005 체크리스트로 남긴다.

| # | 검증 항목 | 결과 |
| --- | --- | --- |
| 1 | **ONNX ↔ torch 수치 동등성** | ✅ 상대차 **6.2e-07** — 임계값 이식 가능 |
| 2 | ONNX 정적 shape | ✅ `[1,3,256,256]` → `[1]`, `[1,1,256,256]`, 동적축 0 |
| 3 | opset / IR 버전 | ✅ opset **14**, IR **7** — JetPack 6 TensorRT·ORT 지원 범위 |
| 4 | `onnx.checker` | ✅ 통과 (335 노드 / 33종 연산자) |
| 5 | **anomalib 없이 판정 재현** | ✅ ONNX + `metadata.json` + `decision.py`만으로 완주 |
| 6 | 판정 밴드 불변식 | ✅ threshold→normScore 0.5, 경계 confidence=0, 양끝 판정 정상 |

**검증 중 발견해 수정한 것**

1. **동적축이 남아 있었다.** `input_size`만 주면 anomalib이 `batch_size`와 `anomaly_map`
   차원을 동적으로 남긴다. 특히 `anomaly_map`은 Reshape에서 파생된 이름 없는 동적 차원이라
   **TensorRT shape 추론이 깨지기 쉽다.** → `onnx_kwargs={"dynamic_axes": {}}` 적용.
2. **`cv2.CAP_DSHOW`는 Windows 전용**이다. Linux(Jetson)에는 없어서 카메라 스크립트를
   Jetson에서 돌리면 백엔드 강제가 실패한다. → `sys.platform` 분기로 V4L2 선택.
3. **판정 계산식이 `train.py`(torch 의존)에 묶여 있었다.** 추론 측이 재사용하면 torch를
   끌어오게 된다. → **`decision.py`로 분리**(numpy만 의존). 학습·추론이 같은 함수를 쓴다.

**⚠️ 전처리 계약 (반드시 준수)**

**ONNX 그래프는 ImageNet 정규화를 포함하지 않는다**(실측 확인: 정규화 입력 173.24 vs
[0,1] 원본 52.55). 즉 **추론 측이 정규화를 직접 적용해야 한다.** 빠뜨리거나 두 번 적용하면
점수가 3배 이상 어긋나 임계값이 무의미해지는데, **에러 없이 조용히 틀린다.**
정규화 파라미터는 `metadata.json`의 `input.normalization`에 있고 `decision.py`가 읽는다.

**메모리 예산 (실측 기반 산정)**

메모리뱅크 행수 = `학습장수 × (입력/8)² × coreset_ratio`, 차원 1536(wide_resnet50_2 layer2+3).
**ONNX는 메모리뱅크를 2벌 저장한다**(원본 + MatMul용 전치) — 이 중복이 크기를 지배한다.

| 학습 장수 | coreset | 뱅크 행수 | 뱅크 | ONNX 총 크기 |
| --- | --- | --- | --- | --- |
| 100 | 0.1 | 10,240 | 60 MB | 215 MB |
| 100 | 0.05 | 5,120 | 30 MB | 155 MB |
| 200 | **0.1** | 20,480 | 120 MB | **335 MB** ⚠️ |
| 200 | **0.05** | 10,240 | 60 MB | **215 MB** ← 권장 시작점 |
| 200 | 0.01 | 2,048 | 12 MB | 119 MB |

Orin Nano는 CPU·GPU가 **8GB를 공유**하고 여기에 얼굴 매칭 모델과 YOLO가 함께 올라간다.
`DATA_COLLECTION.md`의 목표 수량(150~200장)에서 기본 `coreset_ratio=0.1`을 쓰면 ONNX만
335MB다. **`0.05`에서 시작해 정확도 손실이 보일 때만 올리는 것을 권장**한다.

**GATE-005에서 실기로 확인해야 할 잔여 항목**

- [ ] **TensorRT 변환** — `Range`, `TopK` 연산자가 포함돼 있다. 최신 TensorRT는 지원하지만
      변환 실패·성능 급락 가능성이 있으므로 실측한다. 실패 시 **onnxruntime-gpu 폴백**.
- [ ] **onnxruntime ARM64/JetPack 6 빌드 확보** — PyPI 일반 휠이 아니라 Jetson용을 써야
      CUDA/TensorRT EP가 붙는다.
- [ ] **numpy 버전 정합** — 학습 측은 numpy 2.2.6. Jetson의 onnxruntime 빌드가 요구하는
      numpy 계열(1.x일 수 있음)과 맞는지 확인. `decision.py`는 numpy 1/2 양쪽에서 동작한다.
- [ ] 3종 모델(얼굴·YOLO·PatchCore) **상주 vs 온디맨드 로딩** 메모리·전환 지연
- [ ] 콜드스타트 워밍업, 발열 스로틀링, 반납 검수 **5초 타임아웃** 충족 여부
- [ ] 동일 이미지로 **Jetson ONNX 점수 ↔ 학습 측 점수 재대조**(x86에서는 일치 확인 완료)
- [ ] **SSH 터널 오버헤드 실측**(2026-07-27 신규) — Jetson이 별도 서버(FastAPI 등) 없이
      `127.0.0.1`에만 바인딩하고 Pi가 SSH 포트포워딩(`ssh -L`)으로만 접근하는 구조(`docs/
      API-draft.md` §6-2 "방식 C")로 확정됨에 따라 실기 검증 필요. 확인 항목:
      (a) SSH 암호화가 Jetson ARM 코어에 추가로 얹는 CPU 부담 — 이미 캡처+검출+인코딩이
      CPU를 다투는 상태(개발 PC 실측: 동시 인증 중 fps 10.0→5.2~8.0 저하)라 여기에 더해질
      경우 저하 폭이 커지는지, (b) 실제 두 기기(Jetson·Pi)가 물리적으로 분리된 Wi-Fi를
      거친 터널 지연 — 지금까지의 모든 검증은 개발 PC 한 대 안에서만 했고 실제 네트워크
      홉을 낀 적이 없음, (c) 터널이 끊겼다가 재연결되는 상황에서 스트리밍·`/v1/face-auth`·
      `/v1/damage-inspection` 전부가 정상 복구되는지. 개발 PC(CPU) 벤치마크는 Jetson
      GPU(TensorRT/CUDA) 전환 시 개선될 여지가 있지만, SSH 암호화는 CPU가 처리하는 일이라
      이 개선과 무관하게 별도로 실측해야 함.

> **`.ckpt` 재로딩 주의**: torch 2.6부터 `torch.load`의 `weights_only` 기본값이 `True`라,
> 커스텀 `PreProcessor`가 들어간 우리 체크포인트는 그대로 로딩되지 않는다
> (`weights_only=False` 필요). **ONNX 배포 경로에서는 무관**하나, 재내보내기 시 걸린다.

## 4. Implementation Steps & Scripts

### 추론 파이프라인 (3-컴포넌트: 우산 탐지 → 품질 게이트 → 파손 판정)

반납 이미지를 PatchCore에 **곧바로 넣지 않는다.** 앞단에서 "우산이 맞는지 + 판정 가능한 화질인지"를
거른 뒤에만 파손 판정을 수행한다. 특히 **PatchCore는 비(非)우산을 높은 이상치 = `DAMAGED`로
오분류**하므로(정상 우산만 학습하기 때문), 존재 판별은 반드시 앞단에서 해야 한다.
(v0.2 **FR-INSPECT-001 촬영 품질 검사 / AIR-AI-009 품질 게이트**에 해당)

순차 실행: **① 우산 탐지 → ② 품질 게이트 → ③ 파손 판정**

- **① 우산 탐지 (detection model)** — `stage: DETECT`
  - **COCO 사전학습 경량 탐지기(YOLOv8n, `ultralytics`)** 로 `umbrella` 클래스 검출. COCO에 umbrella
    클래스가 있어 **추가 라벨링 없이 시작**할 수 있다.
  - **역할은 "존재 확인 + 위치 제공"이다(2026-07-22 정정).** 사용자가 우산을 손에 들고 제시하므로
    피사체 위치가 고정되지 않는다. 따라서 **bbox가 ③의 크롭 좌표가 된다**(「판정 로직 (1)」).
    - ⚠️ 이전 개정에서 "존재 확인 전용, bbox 미사용"으로 적었던 것은 **거치대 고정 전제**에
      기반한 것이었다. 시나리오 정정으로 **폐기**한다.
    - **bbox 정밀도가 판정 품질에 직결된다.** bbox가 흔들리면 크롭이 흔들리고, PatchCore는
      그 흔들림을 이상치로 읽는다. → 탐지기 성능 요구가 높아졌고 **파인튜닝 필요성도 상승**했다.
  - ⚠️ **뷰 리스크 (top-down)**: COCO의 umbrella 이미지는 대부분 **사람이 든 측면/사선 뷰**라,
    top-down 캐노피(원형+방사형 살 구조)는 **과소표현**돼 있다. → 펼친 우산 top-down은 검출 신뢰도가
    경계(마진)일 수 있고, **접힌 우산은 거의 실패**할 수 있다.
    - **파일럿 실측(2026-07-22, `check_umbrella.py`)**: 개발 PC 내장캠 + **손에 든 임의 각도**
      90초 구간에서 **검출률 78.0%(conf≥0.25), 검출 시 신뢰도 중앙값 0.918**. 분포가 양극단
      (WEAK 5.7%)이라 **자세 의존성**이 관찰됨. 놓침이 연속으로 뭉치는 구간(최장 5.8초)도 확인.
    - ✅ **시나리오 정정으로 이 파일럿의 대표성이 올라갔다.** "손에 들고 카메라에 제시"가 실제
      운영 방식이므로, 위 78%·5.8초 드롭아웃은 **버릴 수치가 아니라 참고해야 할 실측치**다.
      (여전히 카메라·높이·조명은 다르므로 실기 재측정은 필요)
    - → **파인튜닝을 기본 경로로 본다.** 78%의 나머지 22%는 곧 재촬영·`UNCERTAIN`이고, 5.8초
      연속 놓침은 재시도로도 복구되지 않는다.
  - 우산 미검출 → 재촬영, 반복 실패 → `UNCERTAIN`.
  - **파인튜닝(전이학습, 조건부)**: top-down 우산 이미지에 bbox 라벨을 붙여 소량 학습. PatchCore용
    정상/파손 촬영과 **같은 세션에서 라벨을 함께 확보**하면 추가 부담이 작다 → 지그 촬영 후 결정.
  - **대안**: 고정 지그라 "비우산" 유입이 드물어, top-down YOLO가 끝내 안 되면 탐지기를 빼고
    **규칙(점유율·형태) + PatchCore로 축소**하는 것도 허용 가능한 선택(존재-판별 필요성이 통제 환경에선
    낮음).
- **② 품질 게이트 (규칙 기반, 비학습)** — `stage: QUALITY`
  - **검출된 bbox 영역**이 판정 가능한 상태인지 확인. OpenCV 규칙(비학습).
    - **블러** — 라플라시안 분산. 손에 들고 있으므로 흔들림 블러가 상시 발생한다.
    - **bbox 점유율** — 너무 작으면(멀리 듦) 해상도 부족, 너무 크면 캐노피가 잘림.
    - **프레임 경계 잘림** — bbox가 화면 가장자리에 닿으면 우산 일부가 프레임 밖이다.
    - **탐지 신뢰도** — 경계값(WEAK) 검출은 bbox도 부정확할 가능성이 높다.
  - 품질 미달 → 재촬영, 반복 실패 → `UNCERTAIN`.
  - ⚠️ 손에 든 제시 방식이라 **이 게이트의 중요도가 거치 방식보다 훨씬 높다.** 통제되지 않은
    변동을 여기서 걸러내지 못하면 전부 ③의 오판으로 넘어간다.
- **③ 파손 판정 (PatchCore)** — `stage: DAMAGE_CHECK`
  - 통과한 **bbox 크롭**(정사각 확장 + padding)에만 PatchCore 추론 → Anomaly Score.
  - 정규화 점수·임계값·`UNCERTAIN` 밴드는 아래 「판정 로직 (확정)」에 따른다.

결과 코드는 서버 반납 처리(우산 상태 전이)와 1:1로 연결된다:

| 결과 | 발생 컴포넌트(`stage`) | 우산 상태 |
| --- | --- | --- |
| `NORMAL` | ③ DAMAGE_CHECK | `AVAILABLE` / `DRYING` |
| `DAMAGED` | ③ DAMAGE_CHECK | `ADMIN_REVIEW` |
| `UNCERTAIN` | ① DETECT(우산 아님) / ② QUALITY(화질) / ③ 경계 | `ADMIN_REVIEW` |
| `FAILED` | 임의 컴포넌트 예외 | `ADMIN_REVIEW` |

> **학습 대상 모델은 PatchCore 1개**다(탐지기는 COCO 사전학습 활용, 파인튜닝은 선택). Jetson에 상주
> 하는 추론 종류는 **얼굴 매칭 + 우산 탐지 + PatchCore = 3종**이다. 단, 세 추론은 시점이 분리돼
> (얼굴=인증 단계, 탐지·파손=반납 단계) **동시 실행 경합은 없다.** 실질 성능 변수는 모델 **공존
> (메모리 상주) vs 온디맨드 로딩, PatchCore coreset 크기, 콜드스타트 워밍업, 발열 스로틀링**이며,
> GATE-005 PoC에서 세 추론 합산·전환 지연과 메모리를 실측해 결정한다. (v0.2 RISK-AI-001의 "동시
> 수행 경합" 표현은 Jetson 이관·시점 분리 기준으로는 부정확 → 다음 스펙 개정 시 교정)

### 판정 로직 (확정)

> 아래 수치는 **데이터 확보 전 초기값**이며, GATE-005에서 재조정한다. 다만 *산출 절차와 계약*은
> 확정이다 — 절차가 흔들리면 데이터를 다시 찍어야 하기 때문이다.

#### (0) 촬영 시나리오 (확정, 2026-07-22 정정)

**반납 시 사용자가 우산을 들어 카메라에 비춘다. 카메라는 우산함에 고정(사람 키보다 약간 높은
위치)이고, 우산은 사용자가 손에 든 채 캐노피 외부(윗부분 언저리)를 보여준다.**

| 항목 | 값 |
| --- | --- |
| 카메라 | **고정** (우산함 설치, 성인 키보다 약간 높음 ≈ 1.8~2.0 m) |
| 우산 | **사용자가 손에 들고 제시** — 위치·거리·각도가 매번 다름 |
| 촬영 대상 | 우산 캐노피 **외부 상단** |
| 배경 | **통제 불가** (사용자 신체, 바닥, 주변 환경이 프레임에 들어옴) |

> ⚠️ **초기 설계는 "우산을 거치대에 놓고 top-down 고정 촬영"을 전제했으나, 위와 같이 정정됐다.**
> 카메라만 고정이고 **피사체는 고정되지 않는다.** 이 차이가 아래 설계를 바꾼다:
>
> | 결정 | 거치 전제(폐기) | 손에 들고 제시(현행) |
> | --- | --- | --- |
> | 크롭 | 고정 ROI | **탐지 bbox 크롭** |
> | 탐지기 역할 | 존재 확인 전용 | **존재 확인 + 위치 제공** (정밀도 필요) |
> | 파인튜닝 | 조건부 | **필요 가능성 높음** |
> | PatchCore 난이도 | 낮음(변동 통제됨) | **높음**(거리·각도·회전·배경 변동) |
> | 데이터 수량 | 150~200장 | **상향 필요** (변동을 덮어야 함) |

#### (1) 크롭 = 탐지 bbox (정정)

피사체가 고정되지 않으므로 **① 탐지기의 bbox를 크롭 좌표로 사용한다.**

- bbox를 **정사각형으로 확장**(긴 변 기준)한 뒤 크롭 → `256x256` 리사이즈. 종횡비를 보존해야
  같은 우산이 늘 같은 비율로 들어간다. bbox를 그대로 쓰면 프레임마다 종횡비가 달라진다.
- bbox에 **여백 비율(padding)을 고정**해 적용한다(예: 각 변 5%). 탐지기가 캐노피를 살짝 잘라내는
  경우가 있어, 여백 없이 크롭하면 가장자리 파손이 잘려 나간다.
- **학습·추론이 완전히 동일한 크롭 규칙**(정사각 확장 + 동일 padding + 동일 리사이즈)을 쓴다.
  이 규칙이 어긋나면 임계값이 그대로 무의미해진다.

> ⚠️ **최대 난제 — bbox 안의 배경**: 캐노피는 원형인데 bbox는 사각형이라 **모서리에 배경이
> 들어온다.** 배경은 사용자 신체·바닥·주변으로 매번 달라지고, PatchCore는 그 변동을 곧바로
> 이상치로 읽는다. 정상 우산인데 모서리 때문에 `DAMAGED`가 뜨는 실패 양상이 예상된다.
>
**합성 실험 결과 (2026-07-22)** — 배경 A로 학습 후, 배경만 바꾼 정상 우산과 파손 우산의
점수 상승폭을 비교. `resnet18` / 학습 40장 / 합성 이미지.

| 방식 | 배경 변동 상승폭 | 파손 상승폭 | 판정 |
| --- | --- | --- | --- |
| **크롭만 (마스킹 없음)** | **1.690** | 1.115 | ❌ 배경이 파손보다 **152%** 크게 영향 |
| 캐노피 형상 마스킹 | 0.000 | 0.852 | 🟡 배경은 잡히나 신호 약화 |
| 외곽 실루엣 마스킹 | 0.000 | **−0.105** | ❌ **파손이 정상보다 낮음** (역전) |
| **내접 정사각 크롭** | 0.000 | **3.526** | ✅ 파손 신호가 크롭만 대비 **3배** |

**결론: 배경 민감도는 실재한다.** "bbox의 78%가 천이니 괜찮지 않나"는 통하지 않는다 —
PatchCore의 이미지 점수는 패치들의 **평균이 아니라 최댓값**이라, 모서리 패치 하나가 튀면
그대로 이미지 점수가 된다. 실제로 **배경만 바뀐 정상 우산이 파손 우산보다 높은 점수**를 냈다.

**마스킹은 해법이 아니다.** 배경을 상수로 치환하면 천↔상수 경계에 **인위적인 강한 엣지**가
생기고, 그 경계 패치가 최댓값을 지배해 정작 파손 신호를 덮는다(기저 점수가 25.8 → 36.1로 상승).
실루엣 마스킹은 파손 점수가 정상보다 낮아지는 역전까지 발생했다.

**➡ 권장: 내접 정사각 크롭.** 모서리 배경도, 인위적 경계도 없어 정상 분포가 가장 좁게 잡히고
(기저 23.3으로 최저) 파손 신호가 가장 크게 남는다.

> ⚠️ **내접 크롭의 대가**: 내접 정사각형은 캐노피 면적의 **약 64%(2/π)** 만 덮는다. 즉 **바깥
> 테두리 36%를 버린다.** 테두리 파손(가장자리 찢어짐, 살 끝 휨)은 구조적으로 놓친다.
> → **테두리 파손 비중이 크면** 내접 크롭 대신 ①크롭+**배경 다양화 학습** 조합을 재검토한다.
> 실제 파손이 어디에 주로 생기는지는 파손 샘플 확보 후 확인할 것.

> ⚠️ **위 수치는 합성 이미지다.** 절대값·배율은 실물과 무관하며, 확인된 것은 **메커니즘의
> 존재와 방향**이다. GATE-005에서 실데이터로 4가지를 모두 재측정해 확정한다.

**배경 다양화는 어느 방식을 택하든 유효하다.** 학습 데이터에 다양한 배경·사용자·시간대를
포함시키면 메모리뱅크가 그 변동을 "정상"으로 갖게 되어 민감도가 근본적으로 낮아진다.
→ `DATA_COLLECTION.md §5`에 필수 항목으로 반영됨.

#### (2) `confidence` 필드 정의 (API·ERD 계약)

`inspection-results`·`DamageInspection`은 `confidence` **float 하나**만 갖는데, 단계별로 원래
스케일이 다르다(YOLO는 0~1, PatchCore anomaly score는 **무계**). 그래서 다음으로 **통일 정의**한다:

> **`confidence` = 그 판정에 대한 확신도, 0.0~1.0. 경계에서 0, 확실할수록 1.**

| `stage` | 산출식 |
| --- | --- |
| `DETECT` | YOLO `umbrella` 신뢰도 그대로 (이미 0~1) |
| `QUALITY` | 게이트 항목 중 **가장 나쁜 항목**의 정규화 마진 (통과 시 최솟값, 실패 시 그 항목 값) |
| `DAMAGE_CHECK` | `|normScore − 0.5| × 2` (clip 0~1) |

- `normScore`는 **anomalib의 MinMax 정규화 점수**다. 임계값이 **정확히 0.5로 매핑**되므로 무계
  문제가 사라지고 밴드를 대칭으로 표현할 수 있다. (`NormalizationMethod.MIN_MAX`)
- 원시 anomaly score는 **Jetson 로컬 로그에만** 남긴다(임계값 재조정용). 서버 payload에는 넣지 않는다.

#### (3) 판정 밴드

| `normScore` | 결과 |
| --- | --- |
| `< 0.40` | `NORMAL` |
| `0.40 ~ 0.60` | `UNCERTAIN` (경계) |
| `> 0.60` | `DAMAGED` |

- **밴드 폭 δ = 0.10 (초기값).** 좁게 시작한다 — 넓히면 관리자 확인 대상이 늘고, **실물 슬롯이
  3~5개뿐이라 오탐 1~2건이면 시연에서 가용 우산이 고갈**된다. 오판이 실제로 보이면 넓힌다.

#### (4) 임계값 산출 절차 (과적합 방지)

⚠️ 파손 샘플이 **유형별 15~20장뿐**이라, 파손 샘플에 F1이 최대가 되도록 임계값을 맞추면 그 표본에
과적합된다(그 20장에만 잘 듣는 임계값).

1. **임계값은 정상 데이터만으로 뽑는다.** `test/good`(정상 ~30장)의 anomaly score 분포에서
   **백분위 기준**으로 결정 — 초기 목표는 **정상 오탐률 ≤ 5%(p95)**.
2. **파손 샘플은 검증에만 쓴다.** 그 임계값에서 파손 Recall이 얼마인지 *확인만* 하고,
   **파손 샘플에 맞춰 임계값을 되돌려 조정하지 않는다.**
3. 근거: 정상은 150~200장으로 충분히 많고 파손은 20장 남짓이다. **표본이 많은 쪽 분포로 기준을
   잡는 것이 통계적으로 안정적**이다.
4. 산출된 임계값·백분위·그때의 Recall을 **모델 버전과 함께 기록**한다(`modelVersion`).

> **오탐 vs 놓침 정책**: 일반 서비스라면 "파손 놓침"이 더 위험하지만, **MVP는 슬롯 3~5개짜리
> 시연**이라 오탐의 비용이 비정상적으로 크다(가용 우산 고갈 → 시연 중단). 그래서 **p95에서 시작**하고,
> 시연 리허설에서 놓침이 보이면 조인다. 이 트레이드오프는 데이터 확보 후 재검토 대상이다.

#### (5) 재촬영·타임아웃 정책

| 항목 | 값 | 비고 |
| --- | --- | --- |
| `DETECT` 실패 시 재촬영 | 최대 **2회** (총 3시도) | 초과 → `UNCERTAIN` |
| `QUALITY` 실패 시 재촬영 | 최대 **2회** (총 3시도) | 초과 → `UNCERTAIN` |
| 파손 검수 전체 타임아웃 | **5초** | 초과 → `FAILED` |
| 모델 예외·로딩 실패 | 즉시 `FAILED` | 재시도 없음 |

- 어느 경우든 **물리 반납은 진행**하고 우산만 격리한다(`CLAUDE.md`). 사용자를 세워두지 않는다.
- `DAMAGE_CHECK`는 **MVP에서 단일 프레임 1회 추론**으로 시작한다. 다중 프레임 중앙값 집계는
  점수 노이즈가 실제로 관측될 때만 도입(확장 항목).

#### (6) 결정 순서 요약

```
프레임 취득
  └─ ① DETECT   우산 있나? bbox는?        No  → 재촬영(≤2) → UNCERTAIN
  └─ ② QUALITY  선명한가? 크기·잘림 OK?   No  → 재촬영(≤2) → UNCERTAIN
  └─ ③ DAMAGE_CHECK  bbox 정사각 크롭(+마스킹) → PatchCore → normScore
        < 0.40 → NORMAL   |   0.40~0.60 → UNCERTAIN   |   > 0.60 → DAMAGED
  (임의 단계 예외·5초 초과 → FAILED)
```

### Step 1: Data Preprocessing & Pipeline (`dataset.py` or Config)

카메라 앵글의 미세한 오차와 주변 배경 노이즈를 제어하기 위해 실시간 전처리를 적용합니다.

- **bbox 크롭:** ①이 검출한 bbox를 **정사각으로 확장 + 고정 padding** 후 크롭한다
  (§4 ① · 「판정 로직」(1)). **학습·추론이 반드시 동일한 크롭 규칙**을 쓴다.
  세그멘테이션 마스킹을 도입하면 이 단계에서 배경 픽셀을 치환한다.
- **Resize:** 모델 입력 표준 크기인 `256x256` 픽셀로 변환.
- **Normalization:** ImageNet 표준 평균/표준편차 정규화 적용.
- `anomalib.data.Folder` 모듈을 연동하여 Train 및 Test DataLoader를 자동으로 구성합니다.

> ⚠️ **증강 주의**: PatchCore는 정상의 분포를 외우는 모델이라, 학습 측에 **회전·플립·색상 증강을
> 넣으면 정상 분포가 인위적으로 넓어져 파손 탐지력이 떨어진다.** 우산 회전 다양성은 증강이 아니라
> **실제 회전 촬영**으로 확보한다(`DATA_COLLECTION.md §5`). 학습 변환은 위 3단계(크롭·리사이즈·정규화)로 제한한다.

### Step 2: Model Training & Evaluation (`train.py`) — ✅ 구현 완료

- `anomalib.models.Patchcore`(백본 `wide_resnet50_2` 기본, Jetson 메모리가 빠듯하면 `resnet18`).
- **후처리의 정규화·임계처리를 끄고 원시 anomaly score를 받아**, 임계값을 위 「판정 로직 (4)」의
  절차(정상 분포 백분위)로 직접 산출한다. anomalib 기본값인 test셋 F1 최적화를 쓰지 않는다.
- 평가는 이진 통과율이 아니라 **3단 판정 밴드(NORMAL/UNCERTAIN/DAMAGED)** 로 집계하고,
  운영 지표 2개를 함께 출력한다 — *정상인데 격리된 비율*(가용 우산 고갈), *파손인데 통과한 비율*.
- 산출물: `weights/<modelVersion>/` 아래 **ONNX·`metadata.json`·`scores.npz`·`.ckpt`**.
- 데이터 없이 배선만 확인하려면 `--smoke`(합성 데이터). **정상 데이터만 있어도 전 과정이 동작**한다.

> ⚠️ **anomalib `Folder`의 기본값 함정**: `val_split_mode=FROM_TEST`, `val_split_ratio=0.5`라
> **테스트셋의 절반이 조용히 검증셋으로 빠진다.** 우리는 임계값을 정상 테스트 분포에서 뽑으므로
> 표본이 반토막 나면 임계값 품질이 직접 나빠진다. PatchCore는 1에폭·조기종료 없음이라 별도
> 검증셋이 불필요하므로 `val_split_mode="same_as_test"`로 고정한다.

### Step 3: 추론 파이프라인 (`infer.py`) — ✅ 구현 완료

3-컴포넌트를 통합해 서버 payload까지 만드는 온디바이스 추론부.

- 판정식은 `decision.py`, 크롭은 `crop.py`를 **학습과 공유**한다. 재촬영 2회·5초 타임아웃·
  예외 시 즉시 `FAILED` 정책이 구현돼 있다.
- **모델 없이도 실행된다** — `--model_dir` 미지정 시 ①②만 도는 *게이트 검증 모드*.
  학습 데이터가 없는 지금 단계에서 **품질 게이트 임계값을 실물 사진으로 튜닝**할 때 쓴다.
- PatchCore는 ONNX Runtime으로 돌린다(Jetson에 anomalib 불필요). EP 우선순위는
  TensorRT → CUDA → CPU.

> ⚠️ **전처리 정합은 자동 검증된다 (중요)**: 학습·추론 전처리 불일치는 **예외 없이 점수만
> 조용히 어긋나** 임계값을 무력화하는 최악의 버그다. 실제로 개발 중 **8배 어긋난 사례**가 있었다
> (학습 5.16 vs 추론 42.05). 그래서 `train.py`가 학습 직후 ONNX에 **정규화 적용/미적용 두
> 가지를 모두 넣어 학습 점수와 맞는 쪽을 실측 확정**하고 `input.normalization.apply`에 기록한다.
> 추론은 그 값을 읽어 쓴다. **이 값을 손으로 바꾸지 말 것.**
>
> 부수 발견: 현 구성에서 anomalib 학습 경로는 ImageNet 정규화를 모델 입력에 적용하지 **않는다**
> (`apply=false`). PatchCore는 거리 기반이라 학습·추론이 일관되면 동작하지만, 정규화를 적용하면
> 사전학습 백본의 특징 품질이 나아질 여지가 있다 → GATE-005 튜닝 항목.

- **처리 흐름:**
    1. 카메라 프레임 입력 ➔ **① YOLOv8n 우산 탐지**(존재 확인. 미검출→재촬영≤2회→`UNCERTAIN`)
    2. **② 품질 게이트**(블러·점유율·ROI 이탈) 통과 → **고정 ROI 크롭** → 리사이즈·정규화
    3. **③ PatchCore(ONNX) 추론** ➔ raw score → `normScore` → 판정 밴드 적용
    4. `inspection-results` payload 생성 (`stage`·`result`·`confidence`·`modelVersion`·`latencyMs`)
- 판정에 필요한 값은 전부 `metadata.json`에서 읽는다. **`train.py`와 계산식이 어긋나면 안 된다**
  (`to_norm_score` / `classify` 참조).
- 개발 PC 검증용 GUI(원본 + 히트맵 나란히, 판정 오버레이)는 선택. 운영 경로는 헤드리스다.

## 5. Execution Commands

개발 및 시연 시 터미널에서 실행할 표준 명령어입니다.

```bash
# 1. 의존성 설치 (학습 환경 전용. Jetson은 ONNX만 받으므로 불필요)
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu124
pip install -r requirements.txt
pip install --force-reinstall --no-deps "opencv-python==4.11.*"   # headless 덮어쓰기 복구

# 2. 데이터 없이 파이프라인만 검증 (합성 데이터)
python train.py --smoke

# 3. 모델 학습 실행 (고정 ROI는 지그 캘리브레이션 값으로)
python train.py --data_path datasets/umbrella --roi 120,300,720,720

# 4. 추론 속도가 느리면 coreset을 낮춘다 (DESCRIPTION.md §6)
python train.py --data_path datasets/umbrella --backbone resnet18 --coreset_ratio 0.05

# 5. 우산 인식 각도 확인 (탐지 게이트)
python check_umbrella.py
```

학습 산출물은 `weights/<modelVersion>/`에 남는다:

| 파일 | 용도 |
| --- | --- |
| `weights/onnx/model.onnx` | **Jetson 배포 대상** |
| `metadata.json` | 추론 측 판정 계약 — ROI·정규화·`rawThreshold`·밴드·`modelVersion` |
| `scores.npz` | 원시 점수/라벨. 재학습 없이 **임계값만 재조정**할 때 사용 |
| `lightning/.../model.ckpt` | 학습 측 보관용 (재현·재내보내기) |

> `metadata.json`의 `modelVersion`은 서버 `DamageInspection.modelVersion`(FR-INSPECT-007)에
> 그대로 실린다. 임계값을 바꾸면 **반드시 버전을 올려** 판정 이력을 추적 가능하게 유지한다.

## 6. Development Notes & Tuning Constraints

- **촬영 뷰 통일 (top-down):** 운영이 **위에서 내려다본 top-down 뷰**이므로, **탐지·품질·PatchCore의
  데이터 수집과 학습을 모두 top-down으로 통일**한다. 측면 데이터로 학습하면 실환경에서 무의미하다.
  COCO 사전학습 YOLO의 top-down 검출 신뢰도는 **GATE-005에서 우선 측정**하고, 낮으면 파인튜닝으로
  전환한다(§4 ① 참고).
- **조명 통제:** 측면 사광(Side Lighting)을 유지하여 우산살의 능선 그림자가 항상 명확히 드러나도록 세팅해야 합니다. (top-down 카메라 + 그레이징 측면광 조합으로 능선 그림자를 확보)
- **하이퍼파라미터 조정:** 추론 속도가 느릴 경우 `train.py` 내의 `coreset_sampling_ratio` 값을 기본값(0.1)에서 `0.05` 또는 `0.01`로 낮춰 메모리와 연산량을 튜닝할 수 있도록 설정 변수를 상단에 노출해 주세요.1
