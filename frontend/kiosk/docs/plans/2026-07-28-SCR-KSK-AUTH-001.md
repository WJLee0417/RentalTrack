# PLAN: SCR-KSK-AUTH-001 — 얼굴 인증 화면 (Phase 2 첫 화면)

> Phase: **Phase 2 (SCR-KSK-RENTAL, PHASE.md 기준)** — 3개 화면(SCR-KSK-AUTH-001 / SCR-KSK-RENT-001 / SCR-KSK-ERROR-001 대여 variant) 중 첫 번째
> 대응 문서: `docs/09-screen-flow.md` §3.2 SCR-KSK-AUTH-001
> 다음 PLAN에서 다룰 것: `SCR-KSK-RENT-001`(대여 진행·슬롯 안내·완료), `SCR-KSK-ERROR-001`(`UNSETTLED_BLOCKED`, `ACTIVE_RENTAL_EXISTS`)

## 1. 구현 목표

메인 화면에서 "대여" 버튼을 누른 뒤 진입하는 얼굴 인증 화면을 구현한다. 09번 문서 §3.2 기준 4개 Variant(`FACE_CAPTURE` / `FACE_PROCESSING` / `FACE_NOT_DETECTED` / `FACE_NOT_MATCHED`)에 더해, 실제 키오스크 UI 목업(2026-07-28 사용자 제공 스크린샷)을 반영해 **`FACE_CAPTURE` 진입 전 안내 화면(`GUIDE`)**을 새 Variant로 추가한다. Mock 인증 API + 전용 상태 관리로 구현하고, 인증 성공 시 다음 화면(대여 진행, 다음 PLAN에서 구현)으로 넘어갈 수 있는 지점까지 만든다.

- PHASE.md Phase 2 구현 범위 중 "대여 시작 화면"(= 메인 화면 대여 버튼 클릭 → `GUIDE` 화면 진입), "얼굴 인증 화면", "얼굴 인증 API(Mock)", "인증 성공/실패"에 대응한다.
- "대여 진행 화면", "슬롯 안내", "대여 완료 화면"은 다음 PLAN(`SCR-KSK-RENT-001`) 범위다.
- 대응 API 후보: `KSK-AUTH-001`(얼굴 인증 시작) + `KSK-SESSION-002`(세션 상태 폴링) — PROJECT_GUIDE.md §5.4. 이 PLAN에서는 두 API를 하나의 Mock 함수로 단순화한다(폴링 구현은 이번 범위 밖, 8절 참고).
- **신규 범위(목업 반영)**: 대여 흐름 전체에서 공통으로 쓰이는 3단계 스텝 인디케이터("1 대여 시작 · 2 얼굴 인식 · 3 대여 완료")를 `KioskLayout`에 추가한다. `GUIDE` Variant는 이 스텝 인디케이터의 "1 대여 시작" 단계, `FACE_CAPTURE`/`FACE_PROCESSING`/`FACE_NOT_DETECTED`/`FACE_NOT_MATCHED`는 "2 얼굴 인식" 단계로 표시한다("3 대여 완료"는 다음 PLAN인 `SCR-KSK-RENT-001` 몫).

## 4. 각 파일의 역할

### `src/types/faceAuth.ts` (신규)
- `FaceAuthResult` 상수: `MATCHED` / `NOT_DETECTED` / `NOT_MATCHED` (09번 문서 §3.2 Variant 이름과 맞춤. `AUTH_POLICY_REJECTED`·`ORIN_UNAVAILABLE`은 이 화면 담당이 아니라 제외 — 6절 리스크 참고)
- `AUTH_SCREEN_VARIANT` 상수: `GUIDE`(신규) / `FACE_CAPTURE` / `FACE_PROCESSING` / `FACE_NOT_DETECTED` / `FACE_NOT_MATCHED`
- `slot.ts`와 동일한 패턴(객체 상수 + `typeof`/`keyof` 파생 타입)

### `src/api/faceAuthApi.ts` (신규)
- `authenticateFace(): Promise<FaceAuthResult>` Mock 함수 1개
- `stationApi.ts`와 동일한 패턴: `SCENARIOS`(`MATCHED`/`NOT_DETECTED`/`NOT_MATCHED`) 중 하나를 `MOCK_SCENARIO`로 지정, 실제 네트워크 호출 없이 지연 후 반환

### `src/store/faceAuthStore.ts` (신규)
- 이 화면 전용 상태: `variant`(현재 Variant, 초기값 `GUIDE`), `startCapture()`(GUIDE → FACE_CAPTURE), `authenticateFace()` 액션(Mock 호출 → 결과에 따라 variant 전환)
- `kioskMainStore.ts`와 달리 여기서는 variant를 파생값이 아니라 **상태로 직접 저장**한다 — 이유는 5절 참고

### `src/components/layout/RentalStepIndicator.tsx` (신규)
- 목업의 "1 대여 시작 — 2 얼굴 인식 — 3 대여 완료" 헤더 요소
- `currentStep: 1 | 2 | 3` prop 하나만 받는 단순 표시 컴포넌트. 라벨 3개(`대여 시작`/`얼굴 인식`/`대여 완료`)는 컴포넌트 내부 고정 상수(이 흐름 전용이라 재사용 우려 없음)

## 5. 상태 관리 방식

### 두 스토어의 역할 분리
- **`kioskFlowStore`**: "지금 어떤 화면(Screen ID)에 있는지"만 관리 (MAIN ↔ AUTH ↔ 이후 RENT)
- **`faceAuthStore`**: AUTH 화면 **내부**의 세부 Variant(촬영/처리 중/실패 종류)만 관리

이렇게 나누는 이유: `kioskFlowStore`는 이미 Phase 1에서 "화면 단위 전환"용으로 설계돼 있었고(`screen.ts`의 `SCREEN_ID`와 짝), AUTH 화면 안의 세부 단계까지 여기 넣으면 다른 화면(RENT-001 등)의 세부 상태와 뒤섞여 스토어 하나가 모든 화면의 모든 세부 상태를 다 알아야 하는 구조가 된다. `kioskMainStore`가 MAIN 화면 전용이었던 것처럼, `faceAuthStore`도 AUTH 화면 전용으로 분리한다.

### `kioskMainStore`와 다르게 variant를 상태로 저장하는 이유
`kioskMainStore`는 variant를 저장 안 하고 매번 계산했다(`usableSlotCount`라는 하나의 숫자에서 결정론적으로 파생되니까). 반면 AUTH 화면의 Variant 전환은 **"입력값에서 계산"이 아니라 "이벤트에 따른 상태 전이"**다(예: FACE_CAPTURE에서 "촬영 시작" 이벤트가 오면 PROCESSING으로, PROCESSING에서 Mock 결과가 오면 그 결과에 따라 NOT_DETECTED/NOT_MATCHED/성공으로). 이런 흐름은 파생 계산으로 표현하기 어려워서 상태로 직접 관리한다.

### 상태 구조
```
faceAuthStore:
  variant: AuthScreenVariant   // 초기값 GUIDE
  startCapture(): variant = FACE_CAPTURE  ("준비되었습니다" 클릭)
  authenticateFace(): Promise<void>
    1. variant = FACE_PROCESSING
    2. faceAuthApi.authenticateFace() 호출
    3. 결과가 MATCHED → (다음 PLAN에서 RENT-001로 전환하는 콜백 호출 지점)
    4. 결과가 NOT_DETECTED → variant = FACE_NOT_DETECTED
    5. 결과가 NOT_MATCHED → variant = FACE_NOT_MATCHED
  retry(): variant = FACE_CAPTURE 로 리셋 (재촬영)
```

### 스텝 인디케이터와 Variant 매핑
```
GUIDE                                              → currentStep = 1 (대여 시작)
FACE_CAPTURE / FACE_PROCESSING /
FACE_NOT_DETECTED / FACE_NOT_MATCHED               → currentStep = 2 (얼굴 인식)
(다음 PLAN의 RENT-001 화면들)                        → currentStep = 3 (대여 완료)
```
이 매핑을 스토어나 별도 함수로 자동화하지 않고, `AuthScreen.tsx`의 각 분기에서 `currentStep` 숫자를 직접 하드코딩해서 넘긴다(4절 `RentalStepIndicator` 설명 참고 — 과설계 방지).

### 언제 인증을 시작하나 (촬영 트리거)
09번 문서 §3.2 액션 표(`ACT-KSK-AUTH-001` "얼굴 인증 시작")를 보면 명시적 시작 액션이 있다. 다만 화면이 카메라 프리뷰를 보여주는 순간 자동으로 인식을 시도하는지, 사용자가 버튼을 눌러 시작하는지는 09번 문서에 명확한 트리거 방식이 없다(카메라가 항상 실시간으로 얼굴을 스캔하는 UX가 일반적). 이번 PLAN에서는 **`FACE_CAPTURE` 화면 진입 후 일정 시간 뒤 자동으로 `authenticateFace()`를 호출**하는 방식으로 구현한다(실기기에서는 Orin이 계속 스트림을 분석하다가 얼굴이 잡히면 자동 전이하는 것과 유사한 근사치). 정확한 트리거 방식은 문서 근거가 약해 추후 재확인 필요 항목으로 남긴다(8절).

## 6. Mock 데이터 구조

```ts
type FaceAuthResult = 'MATCHED' | 'NOT_DETECTED' | 'NOT_MATCHED'
```

- `stationApi.ts`와 동일하게 `SCENARIOS`(`MATCHED`/`NOT_DETECTED`/`NOT_MATCHED`) 중 `MOCK_SCENARIO` 하나를 지정해두고 수동 테스트 시 이 배정만 바꾼다.
- 지연 시간도 `stationApi.ts`처럼 임의 범위(예: 800~1500ms — 실제 얼굴 인증은 재고 조회보다 느리게 보이는 게 자연스러워서 조금 더 길게 잡는다)를 둔다.
- `AUTH_POLICY_REJECTED`(정책 거절), `ORIN_UNAVAILABLE`(장치 불가)는 이 Mock에 포함하지 않는다 — 전자는 자격 검증 실패로 `SCR-KSK-ERROR-001`(다음다음 PLAN) 몫이고, 후자는 이번 PLAN 범위 밖(8절).

## 7. 테스트 방법 (수동 확인 기준)

1. `npm run build`, `npm run lint` 통과 확인
2. 메인 화면에서 "대여" 버튼 클릭 → `FaceAuthGuideScreen`(`GUIDE`, 스텝 인디케이터 "1" 활성)으로 전환되는지 확인
3. "준비되었습니다" 클릭 → `FACE_CAPTURE`(스텝 인디케이터 "2" 활성)로 전환되는지 확인(카메라 스트림 이미지 자체는 실제 Orin 장비가 없어 깨져 보일 수 있음 — 이건 이번 PLAN이 고치는 대상이 아님, 8절 참고)
4. `faceAuthApi.ts`의 `MOCK_SCENARIO`를 `MATCHED`로 두고: 잠시 후 `FACE_PROCESSING`(로딩) → 인증 성공 처리 지점까지 도달하는지 확인
5. `MOCK_SCENARIO`를 `NOT_DETECTED`로 바꿔서: `FACE_PROCESSING` → `FACE_NOT_DETECTED` 화면(다시 촬영 버튼) → 버튼 클릭 시 `FACE_CAPTURE`로 복귀하는지 확인
6. `MOCK_SCENARIO`를 `NOT_MATCHED`로 바꿔서: `FACE_PROCESSING` → `FACE_NOT_MATCHED` 화면(홈으로 버튼) → 버튼 클릭 시 메인 화면(`kioskFlowStore` 통한 전환)으로 돌아가는지 확인
7. 메인 화면 복귀 시 이전 인증 관련 화면 상태가 남아있지 않은지(다음에 다시 대여 눌렀을 때 `GUIDE`부터 다시 시작하는지) 확인 — PROJECT_GUIDE.md 도메인 보안 규칙 "사용자 표시 정보는 세션 종료 시 즉시 초기화" 관련
8. Phase 1 화면(MainScreen 등 `currentStep`을 안 넘기는 화면)이 스텝 인디케이터 추가 이후에도 기존 모습 그대로인지 회귀 확인(`KioskLayout` 공통 수정 영향 범위 체크)
9. 콘솔에 에러 없는지, 얼굴 관련 어떤 값도 `console.log`/state에 원본으로 남지 않는지 확인(이 Mock은 애초에 이미지·임베딩을 다루지 않으므로 해당 없음)

## 8. 예상 리스크

- **카메라 스트림 실동작 불확실**: `.env` 파일이 이 저장소에 없어(`VITE_FACE_STREAM_TOKEN` 미설정) `CameraCaptureScreen`의 `streamUrl`이 깨진 이미지로 보일 가능성이 높다. `.env`는 CLAUDE.md 규칙상 이 세션에서 수정하지 않으며, 실제 Orin 장비 연동은 이번 PLAN 범위 밖이다 — 화면이 "카메라 프리뷰는 비어 있어도 인증 흐름(Mock)은 정상 동작"하는 것을 목표로 한다.
- **촬영 시작 트리거 방식 불확실**: 5절에서 설명했듯 "화면 진입 후 자동 시작"으로 구현하지만, 09번 문서에 명시적 근거가 약하다. 실제로는 버튼 클릭 트리거일 수도 있음 — 재확인 필요.
- **재시도 횟수·세션 유효시간 미정(`DEC-SF-010`)**: 09번 문서 §6에 `DECISION_REQUIRED`로 명시돼 있다. 이번 PLAN은 재시도 횟수 제한을 두지 않는다(무제한 재촬영 허용) — 제한을 넣으면 임의로 확정하는 것이 되어 CLAUDE.md 규칙 위반.
- **얼굴 정렬 안내 코드 방식 미정(`DEC-KSK-004`)**: `faceGuidance` 필드를 활용한 실시간 정렬 안내(예: "조금 더 왼쪽으로")는 이번 PLAN에서 구현하지 않는다. `FaceGuideOverlay`는 고정된 가이드 도형만 보여준다.
- **`AUTH_POLICY_REJECTED` 처리 위치 불명확**: 09번 문서 흐름도(§4.1)상 얼굴 매칭 성공 이후 "Spring 정책 검증"에서 미정산/활성 대여 존재 여부를 판정하는데, 이건 이 AUTH-001 화면이 아니라 `SCR-KSK-ERROR-001`(다음다음 PLAN)에서 다룰 예정이다. 이번 PLAN에서 인증 성공(`MATCHED`) 이후 지점은 다음 화면 구현 전까지 임시 콜백(placeholder)으로만 남긴다.
- **`GUIDE` Variant는 09번 문서에 명시적 근거가 없음**: 09번 문서 §3.2의 AUTH-001 Variant 표에는 이 "촬영 전 안내" 단계가 없다. 사용자가 제공한 실제 목업을 근거로 추가하는 것으로, 09번 문서가 최신 실제 디자인을 다 반영하지 못했을 가능성이 있다 — Backend/기획 쪽에 이 화면이 별도 API 상태(`KSK-SESSION-002`의 어떤 상태값)로 존재하는지, 아니면 순수 클라이언트 로컬 UI 단계인지 확인 필요. 이번 PLAN은 후자(로컬 UI 단계, 서버 상태와 무관)로 가정하고 구현한다.
- **스텝 인디케이터를 `KioskLayout` 공용 컴포넌트에 넣는 영향 범위**: `KioskLayout`은 Phase 1의 모든 화면(MainScreen, LoadingScreen, ErrorScreen, SuccessScreen 등)이 공유하는 컴포넌트라, 여기 prop을 잘못 추가하면 기존 화면 레이아웃이 깨질 수 있다. `currentStep`을 옵션(선택적) prop으로 만들어 안 넘기면 기존과 100% 동일하게 렌더링되도록 하는 게 핵심 방어선이다.
- **원형 마커의 실제 의미 불명확**: 목업의 원형 마커 2개 안에 아이콘이 들어있는지, 그냥 장식용 단색 원인지 이미지 해상도로는 판별이 어렵다. 이번 PLAN은 장식용 단색 원으로 구현한다(4절) — 나중에 실제 아이콘이 있는 게 확인되면 교체 필요.
